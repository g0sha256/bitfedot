# Architecture

BitFedot is a controller, not a daemon. The node keeps running whether or not the
window is open; the app only decides *what should run* and shows *what is running*.

## Processes

| Process | Lifetime | Role |
|---|---|---|
| `python3 -m bitfedot` | while you use it (or in the tray) | GUI; writes settings; triggers `apply()` |
| `bitfedot-agent.service` | always, once installed | post-sync hand-over, VPN watch, status notifications, the lock against sleep, daily update checks |
| `bitfedot-bitcoind/tor/fulcrum.service` | per settings | the actual services (systemd `--user`) |
| `bitfedot-mempool-pod.service` (+ db/api/web) | per settings | rootless Podman pod generated by Quadlet |

The GUI and the agent never talk to each other directly. They share
`~/.config/bitfedot/settings.json` (guarded by `flock`, read-modify-write) and both call
`services.apply()`, which is serialised by a second lock.

## The one rule: settings → `apply()`

```
settings.json ──► services.config_files() ───► bitcoin.conf, torrc, fulcrum.conf,
                                               *.service, Quadlet files (rendered)
              ──► services.desired_units() ──► {unit: should it run?}
              ──► services.apply() ──────────► ordered stop → write → ordered start
```

`apply(restart=())`, holding its lock:

1. reads the stored settings — itself, and there: whoever gets the lock applies the latest
   ones, and a copy someone read earlier can never be applied later;
2. renders every file and compares it with the one on disk. A unit whose file differs is
   stale, and so is one listed in `restart` (after a binary upgrade);
3. works out what has to go down — unwanted units, stale units, and everything that
   depends on a unit that restarts (`DEPENDENTS`);
4. stops those in `STOP_ORDER` (Mempool → Fulcrum → Bitcoin Core → Tor), **blocking**
   on each so Bitcoin Core can flush its cache and Fulcrum can close its database. If one
   does not stop, `apply()` ends there with an error — nothing it depends on is taken down
   under it;
5. only now writes the files, when nothing that reads them is running, and has systemd load
   them;
6. starts everything that should run, in reverse order, and then reports whatever systemd
   refused;
7. publishes what it is doing to `~/.config/bitfedot/.activity`, which both the GUI banner and
   other processes read.

Because it is idempotent, every feature reduces to "change a setting, call `apply()`":
stopping one service, *Stop all*, *Shut down the node*, switching network mode, toggling the
sandbox, finishing the initial sync, updating a binary (`restart=[unit]`).

### When it does not get to the end

A file is replaced only after its reader has stopped, so a running service always matches the
file on disk — however an `apply()` ends: a service that will not stop, the app closed, the
power gone. The next `apply()` therefore sees from the files what is left to do. Two things the
files cannot show are written down before anything is touched, in
`~/.config/bitfedot/.apply.pending`: that an `apply()` is under way at all, and restarts that
are owed for another reason than a changed file (a new binary). The record goes when an
`apply()` completes.

While the record exists and no `apply()` is running, `services.unfinished()` is true. The agent
then runs `apply()` again — within its next round, and every few minutes for as long as it
keeps failing — the app does the same when it is opened, and its banner says that a change was
not completed and offers *Finish now*. *Stop services and restart* (before a reboot) and
*Remove services* use the same record: if a service does not stop, or the computer does
not restart after all, the node is brought back. Both ask only what is running to stop:
systemd answers with an error for a unit it does not have — Mempool's, while Mempool is
switched off — and that is not a service that will not stop. For the same reason every
`systemctl` call names one unit; a call that names several does nothing for any of them
when one is missing.

"Restart" and "Tor: reconnect" (`services.restart_unit()`) take the same lock without waiting.
In the middle of an `apply()` they are refused, rather than start a service on files that are
about to be replaced.

## Life cycle of a node

```
phase "new" ──install──► phase "ibd" ──agent sees sync complete──► phase "ready"
                          │                                         │
                          │ bitcoind only, sync profile:            │ full profile: txindex, zmq,
                          │ big dbcache, blocksonly, listen=0       │ chosen network mode, then
                          │ (clearnet unless told otherwise)        │ Tor → Fulcrum → Mempool
```

## Status flow

`node.snapshot()` builds one dict per poll (unit states, Bitcoin RPC, Tor control port,
Electrum port, Mempool HTTP). Every page implements `update(snapshot)`; pages hold no state of
their own beyond staged, not-yet-applied choices. `--demo` swaps in `node.demo_snapshot()`.

## Privilege boundary

Unprivileged (the default for everything): downloads, verification, all services, Tor
(its own instance on ports 9250/9251), containers, sandboxing, read-only security checks.

Privileged, via `hardening.as_root()` — one `pkexec /bin/sh -c` batch per user action, with
every interpolated value validated first (interface names, zone names, IP networks):

| Action | Commands |
|---|---|
| Install / update Tor, tray extension | `dnf install`, `dnf upgrade` |
| Optional apps of kind `dnf` (VPNs, some browsers) | pinned key + repo file, `dnf install` |
| Fedora updates, automatic security updates | `dnf upgrade`, `dnf5-automatic.timer` |
| Strict firewall | `firewall-cmd` (zone `bitfedot`) |
| VPN kill switch | `/etc/bitfedot/killswitch.nft`, `bitfedot-killswitch.service` |

An RPM build should replace this with a polkit policy and a fixed helper (see the roadmap).

## Optional apps

`catalog.py` is a list of declarative `App` entries; `apps.py` implements four delivery kinds:

| Kind | Trust chain | Root |
|---|---|---|
| `archive` | pinned key → detached signature over the archive or its checksum file | no |
| `apt` | pinned key → clear-signed `InRelease` → SHA-256 of `Packages` → SHA-256 of the `.deb`; unpacked into `apps/<id>/` | no |
| `flatpak` | per-user Flathub remote created with the pinned repository key | no |
| `dnf` | vendor repository written with `gpgcheck=1` and a `gpgkey=file://…` that is BitFedot's pinned copy | yes |

Installed versions of `archive`/`apt` apps are recorded in `settings["versions"]`; for `dnf` and
`flatpak` the system is the source of truth and `apps.sync_versions()` mirrors it into settings.

## Updating itself

`selfupdate.py` handles per-user installs (`~/.local/lib/bitfedot`): download the release archive
with `SHA256SUMS` and its signature → verify against `keys/bitfedot/` → unpack beside the live
tree → the new tree must import and pass its own tests → rename live to `bitfedot.previous`, new
to live → restart the agent → offer to restart the app. No key shipped means no installation.
RPM installs and git checkouts are left to dnf and git.

## Sync time estimate

`eta.py` works in transactions (Bitcoin Core's `verificationprogress`), measures the current
speed from samples the agent records once a minute, and weights the remaining work by a relative
cost per transaction: higher once the UTXO set no longer fits in `dbcache`, and higher again for
the final stretch after the release's assumevalid block, where signatures are checked.

## Network exposure

| Port | Bound to | Purpose |
|---|---|---|
| 8332 | 127.0.0.1 | Bitcoin Core RPC (cookie for Fulcrum; an `rpcauth` user for Mempool) |
| 8333 | 0.0.0.0 — *only with inbound clearnet enabled* | Bitcoin P2P |
| 8334 | 127.0.0.1 | Bitcoin P2P target of the onion service |
| 28332 | 127.0.0.1 | ZMQ block notifications (Fulcrum) |
| 9250 / 9251 | 127.0.0.1 | Tor SOCKS / control |
| 50001 / 50081 | 127.0.0.1 | Fulcrum Electrum / stats |
| 4080 | 127.0.0.1 | Mempool web + API (also the built-in explorer's backend) |

The Mempool pod reaches the host's loopback through pasta's `--map-host-loopback`, as
`nodehost`; nothing is published beyond `127.0.0.1:4080`.

## Files

```
~/.config/bitfedot/          settings.json, bitcoin.conf, torrc, fulcrum.conf, sync-samples.json
~/.local/share/bitfedot/
    apps/<name>/<version>/   verified binaries (core components and per-user apps);
                             apps/<name>/current → active version
    compat-lib/              library names upstream binaries expect (symlinks to system libs)
    chain/                   bitcoin/, fulcrum/   (location chosen in the wizard)
    tor/                     Tor state and onion service keys
    mempool/                 MariaDB data, backend cache
~/.config/systemd/user/      bitfedot-*.service
~/.config/containers/systemd/  bitfedot-mempool*.{pod,container}
```
